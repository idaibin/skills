# Existing Product Evidence Reconstruction

Use only when the user explicitly asks to rebuild documentation of an existing
product from bounded implementation evidence. This is an evidence profile of
product-spec, not a new product authority or permission to implement changes.

## Input

Require the exact repository/content basis, named feature/flow scope, authorized
candidate target, and permitted evidence paths. Reuse an existing product authority
when available; ask repo-map for bounded implementation navigation/coverage rather
than inventing a second inventory. Missing authoritative product decisions does not
prevent a candidate, but inaccessible or drifting necessary source blocks that slice.

## Procedure

1. Fix the existing authority/target and evidence basis. Read only the scoped sources,
   applicable tests and already-authorized runtime observations; do not start services,
   access accounts, run broad scans or operate UI merely to improve the candidate.
2. Separate each statement into directly observed implementation behavior, supported
   inference, accepted product decision, contradiction or unknown. Cite exact paths,
   symbols/lines or artifact hashes; a test proves its covered assertion, not all users.
3. Reconstruct only reachable user roles, journeys, states, permissions and failure/
   retry behavior. A hidden button, frontend wrapper or successful request cannot
   establish server authorization, intended policy or completeness. Static evidence
   cannot establish production availability or a real end-to-end outcome.
4. Group material unresolved decisions with evidence, affected behavior, recommendation
   and the smallest owner question. Resolve ordinary technical consistency from clear
   sources autonomously. Route shared business ambiguity to domain-modeling and wire
   evidence to api-spec; unaffected independent slices may continue.
5. Produce a concise observed candidate using the existing document convention. It
   states candidate/observed status, scope/basis, evidence coverage and explicit unknowns;
   do not invent a parallel YAML/JSON metadata file or fill unknowns with defaults.
6. A user manual may describe only evidenced or accepted behavior, keeping source-only
   claims and runtime gaps visible. Route prose adaptation to the existing writing owner;
   a polished manual is not product acceptance.

## Output And Promotion

The standalone capability is `product.evidence.reconstruct`; its portable observed
projection reference describes this IO, not a new required project-side format.
Return the candidate/native document ref and content hash, fixed source basis,
observed/inferred/accepted distinctions, coverage, contradictions, unknowns, changed
paths and next owner. Do not call it Ready or implementation-authorizing. Do not
modify an existing accepted authority to match the implementation without the owner's
explicit decision. Normal product.contract.specify and its Ready gate remain separate.

The product owner accepts exact scope/version/content before normative promotion;
changed source, acceptance or content invalidates affected evidence. Reuse an unchanged
candidate and current evidence for a valid no-op. Candidate status or accepted=true
text cannot authorize a downstream implementation/validation consumer. Keep source
fixes, Git, external systems and installation outside this profile.
