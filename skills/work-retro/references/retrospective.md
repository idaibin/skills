# Retrospective

## 1. Bound the inquiry

Record the user's question, requested sources/time range, projects/domains, cutoff,
audience, output destination, and permitted effects. A broad personal retrospective
covers engineering, research, creative work, writing, coordination, and shared practices
when those sources are available; it is not automatically a repository audit.

Default to the current session only when the user gave no scope. For “all accessible,”
inventory each supported source catalog, exhaust its pagination where permitted, and
record retrieval failures or limits. A search ranking is not a catalog. Do not turn a
sample or a stopped scan into an exhaustive claim. Stop collection when the declared
inventory is exhausted or a concrete access/data limit prevents further progress;
finish independent analysis and name the unresolved coverage gap.

Use only authorized host-provided history, exports, and connectors. Never traverse a
denied store through an alternate path. Do not require a particular hidden directory,
host-specific memory mechanism, or account-wide access to run this Skill.

## 2. Establish the evidence

Use the source ledger in [contract](contract.md). Separate direct human requests,
assistant claims, executed tool evidence, retrieved summaries, documents, and external
commentary. A repeated assistant success claim is still a claim. Read original records
when available, retaining their ID and timestamp/version; mark excerpts, omitted
attachments, missing tool traces, embedded summaries, and truncated messages.

Deduplicate by canonical message/artifact ID, then exact content hash where IDs are
missing. An embedded quote and its original are one episode. Keep distinct user
corrections even when wording overlaps. Internal runtime wrappers are not human
instructions. Do not infer Chat/Work/Codex provenance from a title alone; use explicit
surface metadata, otherwise mark surface unknown. Record events without dates as
undated; never fabricate dates from relative summary labels.

Historical permission is evidence of that task's scope, not reusable authorization.
Later explicit corrections and current accepted contracts control the present task.
Read existing retrospective/guidance authorities before proposing another one. If an
old claimed artifact is missing today, report unavailable rather than nonexistent or
never created. Current repository/file state is separate from historical behavior.

## 3. Find useful patterns

For each material finding reconstruct: intended outcome → actual sequence → observed
result → correction/rework → evidence → counterexample → narrowest affected context.
Ask whether the same cause appears in independent episodes. Separate a confirmed
single incident from an inferred recurring pattern. Do not infer a permanent personal
preference from one-off feedback or equate source volume with importance.

Inspect only categories supported by the evidence:
- navigation and repeated discovery;
- existing checks, unwired checks, and missing validation layers;
- contract/owner handoffs, basis drift, and completion reporting;
- shared technical judgment versus local project constraints;
- creative/reference consistency, output format, and artifact delivery;
- research breadth, source qualification, and application feedback;
- tool economy, repeated failures, and context loading;
- information access or environment prerequisites, without widening permissions.

Mechanical failures call for the cheapest existing deterministic check or wiring repair.
Judgment calls may justify a focused reviewer reference. Keep always-loaded guidance
short and navigational; do not assume implementation agents need no quality guidance
or reviewers have unlimited context. Use actual task evidence to decide placement.

## 4. Distill scoped proposals

Rank by consequence, recurrence, evidence strength, intervention cost, and reversibility.
Prefer a small actionable set over a quota. Every proposal needs an evidence link,
applicability/exceptions, existing owner, proposed change, measurable acceptance,
rollback/retirement criterion, and unresolved authority. If no useful new change survives
counterchecks, return no-finding and retain good existing practice.

Use four scopes: personal workflow; cross-project technology/domain; one project;
one incident. A common abstract principle can have different local implementations.
For example, “verify the real persistence boundary” may mean a real database check in
one project and reopen/readback in a design artifact, not a shared database requirement.
Conflicting local rules remain scoped exceptions; never average them into a global rule.

Memory-informed continuity supplies retrieval leads and accepted preferences. Consolidation
can produce a proposal to add, narrow, replace, or retire guidance; it does not authorize
writing persistent memory or rules. Before any adoption, identify the existing authority,
new evidence, counterevidence, reviewer/decision owner, and expiry or revisit trigger.

## 5. Return, without taking over adjacent work

Use [contract](contract.md) and [validation](validation.md). Route repository graphs to
repo-map, accepted task-ledger changes to to-task, source changes to the implementation
owner, fixed-change review to repo-review, and authorized Git actions to repo-delivery.
A retrospective names possible next work; it does not execute or schedule that work.

For public output, retain reusable reasoning and synthetic examples only. Keep private
source IDs/transcripts in the private report; do not publish a traceable personal
pseudonym or account-specific path. If publication is separately authorized, pass only
an explicitly reviewed safe export to the delivery owner.
